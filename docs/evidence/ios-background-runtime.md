# Isolated iOS full-preseal runtime evidence

G4 owner components exist in `apps/mobile/modules/footage-transfer/ios/Background{Ledger,Preseal,Session,Runtime}.swift`. They are not registered with Expo, the bridge, the UI, or production receiver routes. Production activation remains **NO-GO**. Android and iPhone support in the same app remains required. This is chunk transport and native ledger evidence, not a completed background-upload feature or a passed G4/G5 acceptance gate.

## Native interface

`BackgroundRuntime` is instance-owned, not a lazy React singleton. Its initializer requires a storage directory, explicit initial-creation policy, dedicated Keychain service, native `BackgroundControl`, cellular policy, and a thread-safe active/unlocked observation. Optional native app-scoped `BackgroundServerTrust` supplies private receiver trust. Without that adapter the session uses system TLS, not an accept-all policy. A process-wide claim refuses a second live owner of `footage.sealed.background.v1`; a directory `flock` also refuses competing ledger writers.

- `prepare(BackgroundSelection)` synchronously stages, hashes, sets up, and seals on its serial native queue. The caller belongs on a native worker. The selection contains native receiver/device/epoch/destination binding, never a bearer. The control owner must validate that binding against its own installed pairing and confirmed destination.
- `restoreAndStart(completion:)` enumerates the stable session before scheduling. Its Boolean reports command processing, not receipt or immediate network execution.
- `cancel(completion:)` persists intent and one revoke operation ID before stopping daemon tasks. Offline control cannot confirm remote cleanup.
- `collectCancelled(completion:)` deletes cancelled bulk only after authenticated remote cleanup and an empty `getAllTasks` result. Repeated collection is idempotent. It retains the manifest, outcome keys, and minimal tombstone.
- `snapshot()` returns native phase, original/confirmed byte counts, sealed group count, whether the complete current batch is scheduled, and pending cleanup. No credentials or selected URI leave this owner.
- `handleBackgroundEvents(_:completion:)` accepts main-actor completion tokens. Unknown identifiers complete promptly on main without touching their sessions. Owned tokens accumulate until `urlSessionDidFinishEvents` and ordered durable delegate processing drain. G5 must retain the runtime before JS and forward each subscriber callback once. Tests cover multiple tokens and repeated finish notifications, not a built Expo relaunch.

`BackgroundControl` has no default implementation. It accepts the existing G2 `Manifest` for setup and the existing G2 `Query` for status/revoke. It returns canonical bounded setup/status bytes, which the runtime verifies through `SealedProtocol`. It must perform pairing-authenticated, exact-origin, nonredirecting HTTPS operations with operation masks `0x01`, `0x02`, and `0x04`. It cannot accept a server-supplied upload URL. `BackgroundServerTrust` returns only a native server-trust credential; HTTP authentication never consults a credential store.

## Persistence and packet ownership

The original copy/hash loop uses 64 KiB buffers, source descriptor/path identity checks, and before/after size and modification checks. It computes whole-file and 8 MiB frame hashes during staging. Sealing rechecks each frame hash and the staged whole hash. Eight frames form a group, except the final remainder. All groups must finish before phase `ready`; the complete batch must be durably bound and resumed before `backgroundReady` is true. Losing the injected active/unlocked condition blocks preparation. There is no UIKit background assertion, refill callback, or plaintext retry.

The `.complete` private directory holds the staged original and canonical manifest. Ciphertext and the minimal ledger use after-first-unlock protection, private permissions, and backup exclusion. Each generation master is a new immutable `AfterFirstUnlockThisDeviceOnly`, nonsynchronizing Keychain item. A separate Keychain ledger identity blocks creating an empty replacement after the entire directory disappears. Missing or inaccessible data throws or blocks; it does not regenerate a generation key.

SQLite uses verified WAL, `synchronous=FULL`, `fullfsync=ON`, and startup `quick_check`. Each bounded state replacement is one immediate transaction. A consumed intent with a unique seal ID commits before each production G2 AES invocation. Any interrupted preparation blocks the generation on reopen. There is no resume-sealing API. Exceptions at encryption, file publication, or ledger publication retain burned identities and uncertain partials; retries use exact saved ciphertext only.

File publication synchronizes an exclusive private partial, atomically links its immutable final name without overwrite, unlinks the partial, and synchronizes the directory. This has the required file-before-row ordering without an overwriting rename. A crash can leave an extra partial name or a final orphan, but cannot authorize resealing. Both stay blocked until cancellation/reconciliation permits collection. Tests do not simulate power loss or storage-controller failure.

A correlation UUID commits before task creation. File upload tasks begin suspended. Their task ID commits before `resume`, with another saved transition afterward. Reassociation joins task ID and correlation, never URL alone. Unknown/duplicate tasks cancel and require authenticated reconciliation before replacement. An unknown task without any local job blocks new preparation. A missing task triggers a fresh challenged status query before exact-packet retry. Authenticated ranges and high-water revision never regress. Only the matching final receipt can produce `received`; acknowledgments can produce `verifying`, not finality. A verified immutable final receipt may win a local cancel race.

The background session disables cookies, shared credentials, and cache. Its fixed ingest request has only binary ciphertext framing and content type. The task description is a nonsecret local UUID. Per-task response buffers cap at 4 KiB. Real Simulator uploads exposed an important callback difference: data and task completion arrived without the optional response-header callback. The implementation now checks `task.response` when collecting data too. The real daemon test failed before that correction and passes afterward.

## Executed native checks

Runner: `python3 scripts/test/ios-background-runtime/run.py`. The faster `--unit-only` mode builds and executes the native fault tests without the listener experiment. Both modes create and delete their own Simulator. They never use a booted-device alias.

The complete run uses Xcode 27.2 build 27B52, the iPhoneSimulator 27.2 SDK, and a disposable iPhone 16 Simulator running iOS 26.2. Production G2 and all four G4 sources compile with Swift 6 and warnings as errors. The same owner sources also compile against the iPhoneOS SDK for `arm64-apple-ios17.0`; that is not physical execution evidence.

The 32 native fault tests pass. They cover consumed/encrypted/published/recorded seal boundaries, setup persistence, ledger reopen, exact packet retry, missing task status, stale challenges, chunk versus receipt, before/after task binding/resume, cancellation before resume, late acknowledgment fencing, immutable final receipt races, offline revoke identity, missing key/file/database/directory, unknown/duplicate tasks, oversized fake success, active/unlocked loss, failed SQLite writes before cancel, injected ENOSPC partial retention, idempotent daemon-reference-aware cleanup, and main-thread event completions after durable drain. Separate `_exit(77)` runs stop the app after consumed intent, AES output, and group publication. Reopen refuses to reseal or create tasks and retains consumed identities.

The live test creates **134,230,073 synthetic original bytes** and fully seals three groups. A destination-scoped XCTest presses Home. The app reports `applicationDidEnterBackground`; the runner then SIGSTOPs that exact app PID. The listener begins consuming bodies only after that stop. While the process remains stopped:

- The owned `nsurlsessiond` has the receiver socket.
- The listener reads 134,231,341 ciphertext-body bytes and authenticates all three groups with the production Node G2 codec.
- Its independent streaming concatenation matches the native manifest's complete original size and SHA-256.
- Every received wire hash matches the saved native packet file. Authorization and Cookie header counts are both zero.

After SIGCONT and an explicit XCTest activation of the owned app, native callbacks commit all original ranges. The durable state is `verifying`, with 134,230,073 confirmed bytes and **no received outcome**. The listener has no durable receiver receipt publication and issues no final receipt. This run proves daemon delivery without JS or plaintext reads, followed by chunk ledger reconciliation. It does not prove no-JS cold-launch final receipt delivery.

The final successful run records 385,122,304 bytes of app peak RSS through Debug preparation/scheduling. Runtime files occupy 268,639,180 logical bytes and 268,673,024 allocated bytes. Those files include the staged original, ciphertext, ledger, and metadata, but exclude the separately generated selected test input. All test documents together occupy 403,920,355 logical bytes. These are workload-scoped observations, not RSS/storage bounds. Daemon-owned snapshot allocation, 4 GiB originals, 64 queued tasks, release builds, and physical-device budgets remain unmeasured. The conservative admission check is not a universal free-space guarantee. ENOSPC is injected at a real sealing boundary; the runner does not fill shared disk.

The final successful run deletes its Simulator, stops its listener, and leaves only ignored local build/log artifacts. Fresh test Keychain data disappears with that disposable device. Raw keys, local identities, paths, and media are not public evidence.

## Exact integration constraints and remaining gates

1. **G2 locked-context mismatch.** `Keys`, `VerifiedAck`, `VerifiedReceipt`, and `VerifiedStatus` require a complete `Manifest`. That includes filename, destination, and frame hashes. G4 requires the canonical manifest to stay in a separate `.complete` record and locked event processing not to need it. The current G2 API cannot satisfy both. This runtime does not weaken protection or duplicate the verifier. It saves callback uncertainty before opening protected material and defers when unavailable. G2 needs an independently reviewed minimal immutable outcome context before locked cold-launch processing can pass. Warm unlocked Simulator delivery is not that proof.
2. **G1 authority access.** A combined G1/G2/G4 Swift 6 warnings-as-errors iPhoneOS compile fails at the unchanged `PairingWire.swift:71` deprecated `String(cString:)` call. G2 and the owned G4 sources pass independently. That G1 diagnostic needs its owner's fix; this slice does not suppress it. `PairingClient` exposes installation status but no installed credential/job-control interface. This slice does not edit it. A native G1-owned adapter must acquire the manifest-bound device credential and verify permission, scope, epoch, expiry, exact origin, and confirmed destination. The listener test injects fresh synthetic setup material through private local files. It is explicitly not a production pairing or authenticated control implementation.
3. **G3 finality.** The listener is not the other worker's durable receiver. It authenticates groups and independently checks the original but has no shared receipt publication, receiver restart repair, or OS key wrapping backend. No live endpoint was invented to hide that gap. Synthetic codec receipt tests verify native acceptance rules only.
4. **G5 lifecycle.** No subscriber, generated Expo provider registration, module facade, app config, or JS code changes exist here. Published installed Expo 58.0.21 and core 58.0.28 sources were read at `ExpoAppDelegate.application(handleEventsForBackgroundURLSession:)` and the subscriber manager's aggregation. Native drain tests do not prove that actual app registration, cold launch, deadlines, or multiple wake batches work.
5. **Protected data and retention.** Simulator returns no `protectionKey` file attribute for this test, so successful attribute-setting is not physical protection evidence. Before first unlock is unsupported. Missing protected data never becomes an empty/restored upload. Physical lock/daemon-copy protection, natural OS termination/relaunch, local-network denial, Android app behavior, and force-quit behavior remain later gates. There is no automatic restart promise after force-quit. Keys/private manifest/tombstones remain retained; expiry-plus-reconciliation-period key collection and replacement-generation workflow are not implemented.
